## 一、家底：现在已经有什么（实测清点）

| 文件 | 行数 | 干什么 |
|---|---|---|
| `lib/mod/lan_sync_server.dart` | 258 | 手机上的 HTTP 服务：`GET /`（面板）、`POST /pair`（配对拿 token）、`GET/POST /bundle`（取/交数据）|
| `lib/mod/lan_panel.dart` | 312 | 浏览器面板（单个 HTML+JS 字符串）：查看 / 打钩 / 删除 / 新建 / 导出 / 导入 |
| `lib/mod/lan_sync_page.dart` | 182 | App 内的入口页：开服务、显示地址与配对码 |
| `lib/utils/data_sync.dart` | 179 | **数据契约** `DataBundle`：`format='celechron-mod'`、`exportedAt`、`tasks`、`tombstones`、`tags`、`tagColors`、`reminderMode`、`alarmTheme`；合并结果 `DataMergeResult`（added/updated/removed）|
| `lib/utils/data_backup.dart` | 91 | 文件导出/导入（同一份契约，走文件而不是网络）|
| `lib/model/tombstone.dart` + `lib/mod/database_mod.dart` | — | **删除墓碑**：合并时判断「这条是被删掉的」而不是「对方新增的」|

**已经有底子的地方（很重要）**
- ✅ 数据契约是**版本化 + 传输无关**的（`DataBundle` + 墓碑），加新传输方式是**加法不是重写**；
- ✅ 已经有**两条**通路：网络（`/bundle`）与文件（导出/导入）；
- ✅ 合并逻辑有 `added/updated/removed` 统计，能如实告诉用户改了什么；
- ✅ 配对机制（token）已经有了。

**现在的缺口**
- ❌ 只同步 **待办 / 标签 / 少量设置**：`dbFocus`（专注记录）、附件文件、其它设置**都不在里面**；
- ❌ 面板是「手机当服务器」的单向心智：PC 端本质是遥控器，**不是对等端**；
- ❌ 没有**设备身份**：看不出「这条是哪台设备改的」，也没有「同步到哪些设备」的概念；
- ❌ 没有**实时推送**：现在是一次性的取/交，不会自动感知对方的变化；
- ❌ 冲突策略是**整条 last-write-wins**（靠 `updatedAt`），没有分字段合并；同一秒两边改会丢一边。

## 二、要先想清楚的六件事（需要拍板）

> 每条都给了我的建议，你直接说「按建议」或者改哪条都行。

### 1. 目标形态是什么？

| 选项 | 含义 | 代价 |
|---|---|---|
| **A. 手机 ⇄ 电脑（浏览器）** | 保持「手机当服务器」，把面板做成**真正的编辑器**（改描述/子待办/标签/优先级/地点）+ 自动刷新 | 小 |
| **B. 手机 ⇄ 电脑（桌面 App）** | `flutter build windows` 出真客户端 | **大**（workmanager 11 处、通知 18 处不支持 Windows）|
| **C. 多台手机互联** | 手机之间同步（同一 Wi-Fi 直连）| 中 |
| **D. 跨网络（WebDAV/自建）** | 不在同一 Wi-Fi 也能同步 | 中，但需要用户自己配网盘 |

**建议**：先把 **A 做扎实**（它是所有形态的公共地基：契约、合并、冲突、面板），
之后 C 是「同一套协议换对端」，D 是「同一套协议换传输」，**都不会白干** ✗
不建议一上来就 B（被平台限制拖住）。

### 2. 同步什么数据？

| 数据 | 现在 | 建议 |
|---|---|---|
| 待办 + 标签 + 墓碑 | ✅ 已有 | 保持 |
| **专注记录 `dbFocus`** | ❌ | **建议加**（你已经有统计页，多端一致才有意义）|
| 附件文件 | ❌ | 建议**第二阶段**：按内容 sha1 命名，懒下载（BACKLOG 2）|
| 专注参数/提醒提前量/闹钟配色 | 部分已有 | 建议纳入（都是小标量）|
| 课表/成绩/校园卡 | ❌ | **不建议**：它们是从学校服务器拉的「可重新获取」的数据，同步只会带来陈旧与冲突 |

### 3. 冲突怎么定？（现在是最弱的一环）

**建议**：从「整条 last-write-wins」升级为**三档策略**，并**把结果告诉用户**：
1. 墓碑优先（删掉的不会被对方复活）；
2. 同一条两边都改 → 比 `updatedAt`，新的赢；**但如果两边都改动过同一个「字段组」**，
   就提示一句「这条在两端都改过，保留了较新的那版」（不静默丢弃）；
3. `added/updated/removed` 统计继续显示。

> 想更细（分字段合并）代价大、收益低；**除非你遇到过「两端各改一半」的真实场景**，否则不值得。

### 4. 谁是对等方？（设备身份）

**建议**：给每台设备一个 `deviceId`（首次运行生成、存本地），`DataBundle` 里带上
`deviceId` + `exportedAt`。好处：面板上能显示「最后同步来自 手机 / 客厅台式机」，
将来排查「谁把我这条改了」有据可依。

### 5. 同步是「手动」还是「自动」？

| 方式 | 体验 | 代价 |
|---|---|---|
| 手动按钮 | 现在这样 | 0 |
| **打开面板时自动拉一次 + 改完自动推** | 够用且简单 | 小 |
| 长轮询/SSE 实时推送 | 最爽（另一端点一下，这边立刻变）| 中，且要处理重连 |

**建议**：先做「**自动拉 + 自动推**」（面板与 App 两侧都做），实时推送留到有人抱怨延迟再说。

### 6. 安全边界

现在：同一 Wi-Fi + 配对 token（明文 HTTP）。
**建议**：至少做到 ① token 每次开服务重新生成、② 面板显示「当前已连接的设备」、
③ 文档里写明「只在可信 Wi-Fi 用」。**不建议**自己在应用层搞加密——
局域网内 HTTPS 的收益远小于复杂度，真要跨网就交给 WebDAV(HTTPS) ✓

## 三、建议的路线（每阶段都能单独交付、单独验证）

### S1：把「同步什么」补齐 + 设备身份（地基）
- `DataBundle` 加 `deviceId`、`focusSessions`、`focusWorkMinutes/focusRestMinutes/...`
- 契约**只加字段不改老字段** → 老备份文件仍能导入 ✓
- 测试：契约往返 + 合并（含墓碑、含专注记录）

### S2：面板升级成真编辑器（BACKLOG 1）
- 能改描述 / 子待办 / 标签 / 优先级 / 地点；**改步骤时间与清单分组**
- 自动拉取 + 改完自动推；显示「最后同步来自 X」
- 这是你实际用得最多的界面，值得一次做扎实

### S3：附件同步（BACKLOG 2）
- 附件按内容 sha1 命名 → 同一个面板服务加 `/attachment/<sha1>` 端点
- PC 端**懒下载**（点开才拉），手机端上传
- 需要一个「附件清理」策略（孤儿文件多久删）

### S4：跨网络（BACKLOG 3）与/或 手机互联（C）
- 抽 `SyncTransport` 接口：`LocalHttpTransport`（现在这套）/ `WebDavTransport`（用户自配坚果云）
- 数据层完全复用 S1 的契约 ✓

### S5（可选）：Windows 桌面端（BACKLOG 4）
- 只有前面都稳了、并且你真的需要「电脑上常驻」再上

## 四、风险与坑（先记下来）

| 风险 | 说明 / 对策 |
|---|---|
| **半同步状态**：同步到一半断了 | 契约里有 `exportedAt` 与墓碑，重跑一次是幂等的 ✓ 但仍要测「中断后重连」 |
| **时钟不一致**：两台设备时间不一样 → `updatedAt` 比较出错 | 用「谁的时间更晚」只在**两端都改过**时用；并显示改了哪条，不静默丢 |
| **大附件**：几百张截图 | 懒下载 + 只按需拉；不整包传 |
| **扫到就改**：同一 Wi-Fi 里别人拿到 token | 每次开服务重新配对；面板显示连接设备；文档写清 |
| **学校接口限流** | 注意：**课表/成绩不进同步**就是为了避免「两台设备各拉一次还互相覆盖」|
