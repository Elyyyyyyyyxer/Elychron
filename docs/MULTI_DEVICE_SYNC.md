- ✅ 已经有**两条**通路：网络（`/bundle`）与文件（导出/导入）；
- ✅ 合并逻辑有 `added/updated/removed` 统计，能如实告诉用户改了什么；
- ✅ 配对机制（token）已经有了。

**现在的缺口**
- ❌ 只同步 **待办 / 标签 / 少量设置**：`dbFocus`（专注记录）、附件文件、其它设置**都不在里面**；
- ❌ 面板是「手机当服务器」的单向心智：PC 端本质是遥控器，**不是对等端**；
- ❌ 没有**设备身份**：看不出「这条是哪台设备改的」，也没有「同步到哪些设备」的概念；
- ❌ 没有**实时推送**：现在是一次性的取/交，不会自动感知对方的变化；
- ❌ 冲突策略是**整条 last-write-wins**（靠 `updatedAt`），没有分字段合并；同一秒两边改会丢一边。

### 关于「为什么不直接把 App 装到电脑上」（用户问过，记下来）

Flutter 跨平台跨的是 **UI 层与 Dart 运行时**，不是整个 App。所以：
1. **APK 是 Android 二进制，Windows 跑不了** —— 以前能靠微软的 WSA（Windows 子系统 for Android），
   但**它已在 2025 年 3 月停止支持**；剩下的安卓模拟器体验与「顺手的桌面工具」是两回事；
2. **就算为 Windows 重新编译，插件层也过不去**，实测统计（BACKLOG 第 4 项）：
   - `workmanager`（上游自建 fork）**只支持 Android/iOS** —— 11 处
   - `flutter_local_notifications` **不支持 Windows** —— 18 处
   - `MainActivity.kt` / `ECardWidget.kt` 里的校园卡小组件、全屏闹钟、分享接收
     —— **这些功能在 Windows 上本身就不存在**，整层要重写
   - 另有 `Platform.is` 23 处、`PlatformFeatures` 抽象 11 处 —— 说明代码从没打算跨端跑
3. 真想要桌面端，**得先回答「在电脑上干什么」**：
   - 只是「看和改待办」→ **浏览器面板就是最优解** ✓（零安装、任何电脑能开、改完自动同步）
   - 「电脑上常驻提醒 / 离线重度用」→ 才值得上 Windows 客户端（工作量比面板大一个量级）
   - 好消息：`hive` / `flutter_secure_storage` / `path_provider` / `file_picker` /
     `share_plus` / `table_calendar` **都支持 Windows** ✓ 基础不是从零开始

## 六、WebDAV 全平台同步（2026-09-28 起，正在做）

> 用户原话：「开始做更加科学的全平台同步！使用 WebDAV 服务……我想要尽可能简化用户操作流程」。
> 三条拍板：**不做加密**；**要一个校验机制，别每次都把整包拉下来**（省流量）；按建议做预设 + 三步向导。

### 为什么是 WebDAV

局域网同步要求两台设备同时在同一 Wi-Fi，且手机息屏后经常连不上；
用户要的是「手机改了，电脑上就有」。那必须有一个两边随时都能访问的中转，
而 WebDAV 是**唯一一个不用我们自己出服务器**的办法（坚果云 / InfiniCloud / Koofr /
Nextcloud / 群晖 NAS / Alist 都能用），而且和已经造好的 DataBundle + DataMerge 直接接得上。

### 省流量：三层，从便宜到贵，任何一步能断定「不用继续」就收工

| 层 | 请求 | 代价 | 结论 |
|---|---|---|---|
| 1 | `PROPFIND meta.json` 只看 ETag/时间/大小 | 几十字节 | 指纹和本机记的一致 → **收工** |
| 2 | `GET meta.json`（清单，含 revision） | 几百字节 | revision 相同 → **收工** |
| 3 | `GET/PUT bundle.json`（整包） | 整包 | 只有确实需要时才动 |

远端目录：`Elychron/meta.json`、`Elychron/bundle.json`、`Elychron/devices/<设备号>.json`，
**全部由程序自己建**，用户永远不用管目录结构。

### W4：附件文件本体

同步包里附件只有 `name/path/size`，**二进制不过包**（见 `data_sync.dart`）——
所以另一台设备上那一行在、点开是空的。W4 负责把本体搬过去。

远端文件名 = `<来源路径的 FNV-1a 哈希>_<文件名>`，远端目录 `Elychron/files/`。

- **为什么名字里要带哈希**：两台设备上同名不同内容很常见（`IMG_0001.jpg`、`简历.pdf`），
  拿文件名当身份会互相覆盖；而「来源设备上的绝对路径」就在包的 `path` 字段里，
  两台设备各自算必然一致，又天然不会撞。
- **不重复传**：本机记一份索引（远端名 → 上次传出去时的大小），大小没变就跳过。
  名字里不掺内容指纹是**刻意的取舍**：文件内容改了但大小不变时，最多浪费一次流量，
  传错数据的风险为零（每次同步都读全文件做哈希，对手机是大负担）。
- **流量有上限**：默认**关**（第一次打开就把几年的照片全传上去，会把免费额度一把打光）；
  打开后单文件超 50MB 不传、本月上传超 900MB 不传（坚果云免费版是 1GB/月，留余量），
  而且**如实告诉用户有几个没传**，不默默跳过。界面上有「本月流量」一栏。
- 下载侧：先一次 `PROPFIND Elychron/files/` 拿远端的文件清单，再按需下载 ——
  否则"一次同步几十个请求"，在坚果云上很容易被限流。

### 真机上踩到的两个坑（都已写进代码和测试）

1. **坚果云的用户名必须全小写**：`TixerOfficial@outlook.com` → 401，
   `tixerofficial@outlook.com` → 207（服务器 `Basic realm="nutstore"`）。
   处理：预设表标 `lowercaseUsername: true`，输入框里边打边转；
   同时 `WebDavSync.selfCheck()` 保留「先按原样试，401 再试小写」的兜底
   —— **不能无条件转小写**，Nextcloud 那类的用户名是大小写敏感的。
2. **MKCOL 已存在的目录返回 405**（当成成功处理）；**删除 `Elychron/` 根目录返回 403**
   （无害，目录留着不影响）。

### W5：界面重做 + 三个真机 bug（2026-09-29）

用户原话：「电脑端同步了个空气，有文件传输（消耗了月额度，但两个端的额度没有同步），
但是待办没有同步」；随后又说「现在的手机端全平台同步界面有点丑」。

**bug 1：两个端都没上传过整包（这就是"同步了个空气"）**

`WebDavSyncService._run` 一开始没有把 `localRevision` 传给 `WebDavSync.sync()`，
于是 `decideSyncAction` 里的 `localDirty` **永远是 false**：本机自己的改动永远不算
"有改动"，首次同步直接判成 `upToDate` 收工。而附件文件（走 `_syncFiles`，与 action 无关）
照样上传 —— 所以现象正是**流量扣了、待办一条没动**。
修法：用 `DataBackup.currentBundle` 算一次真实 revision 传进去。代价只有一次本地 JSON 编码
（没有网络请求），省流量的三层照样有效。

**bug 2：打开「同步附件文件」开关，什么都不传**

附件上传原来只在 push/merge 时跑。开关打开后如果这段没有数据改动，每轮同步都是"已是最新"，
附件就永远上不去（真机验收时就是这样：开关是绿的，流量一直是 0 B）。
修法：上传**每次同步都跑**（本地只做 stat + 查索引，不产生网络请求），并且点开关时立刻主动同步一轮。

**bug 3：同一份文件被重复上传（自己吃自己的额度）**

从网盘取回来的文件，本机路径是我们自己起的（`task_attachments/1749xxxx_照片.jpg`），
下次再按本机路径算哈希就是**另一个名字**，于是同一份文件被重复 PUT。
修法：本机记一份 `webdav_file_origin`（本机路径 → 远端名），下载时登记、上传时清理。

**"一个端更新了另一个端不能自动更新"（用户问这算不算系统缺陷）**

一半是 bug（上面 bug 1），一半是架构：WebDAV **没有推送通道**，只能定时去问。所以：

- 本机数据一变 → `notifyDataChanged()` → `scheduleSync()`（8 秒，合并连着的多次改动）；
- 每 **3 分钟**主动问一次远端 —— 一次"没变化"的检查只有几十到几百字节
  （PROPFIND 看指纹 + 读 `meta.json`），问勤一点远比让用户干等十分钟划算；
- App 从后台回到前台时也立刻排一轮。

**界面重做（手机端管理页）**

旧版是一列 `CupertinoListTile`：开关、按钮、流量、账号、断开同步全挤在同一个分组里，
而且"断开同步"就在中间，手指一滑就点到了。现在从上到下按「你最常看 → 你几乎不会碰」排：

| 位置 | 内容 |
|---|---|
| 1 状态卡 | 网盘名 + 状态点 + 一句话结论（22pt 大字）+ 上次同步时间 + 具体细节 + 「立即同步」大按钮 |
| 2 流量卡 | 只在传附件时出现；进度条 + 已下载量；额度剩不到 100MB 时整块变橙 |
| 3 同步设置 | 自动同步 / 同步附件文件（两个开关，各自带一句人话说明） |
| 4 账号 | 网盘名 + 用户名 + 地址（点进去能改） |
| 5 危险 | 断开同步，单独一块、沉底、二次确认 |

真机上还发现一处不一致并顺手修掉：分组标题/脚注必须按设置页的写法来
（13pt + 灰 + 左缩进 16，`_headerFooterTextStyle` 那套）。
`CupertinoListSection` 的默认值是 `textTheme.textStyle`（17pt、正文色）——
分组标题比卡片里的列表项本身还抢眼，整页看起来又黑又乱。

「一句话结论 + 具体细节」的拆解规则是**纯函数**，放在 `lib/mod/webdav_status.dart`：

- `describeSyncStatus(...)`：结论 / 时间行 / 细节三行，`running` 优先于一切
  （正在跑的时候还显示「同步失败」会让人以为这轮又炸了）；
- `formatSyncDetail(...)`：清标点、拆括号；
- `compactCounts(...)`：把「删除 0 条」这种纯噪音去掉 —— 它会让人以为"同步把我东西删了"；
- `formatSyncTime(...)`：时间的说法只保留这一份，`WebDavSyncService.formatTime` 只做转发。

单测钉在 `test/webdav_status_test.dart`（16 条）。所以界面上不会再出现
`两边都有改动，已合并（新增 3 条，更新 1 条，删除 0 条，保留 2 条）` 这种标题 ——
它会变成大字「已合并两边改动」+ 小字「新增 3 条 · 更新 1 条」。


### W6：真机上的两个"滚雪球"bug + 坚果云限流（2026-09-30）

用户：「之前同步的时候莫名其妙多同步了大量重复图片」「循环的待办似乎同步起来也有点问题，
电脑端这里就有两个洗头」「坚果云又 HTTP 503 了，这是偶然吗」。

**bug 1：课程资料在两端各留一份，每次同步翻一倍**

`DataMerge.mergeCourseMounts` 按 **本地路径** 去重，而路径是每台设备自己的 ——
从网盘取回来的文件落在各自的 `task_attachments/` 下、名字里还带本机时间戳，
所以同一个文件两端的 path 必然不同：手机一份 + 电脑一份 = 两份，再同步一轮四份。
更贵的是"多出来的那份"本地没文件，于是**每次同步都被当成缺失重新下载一遍**。

修法：按 **名字 + 大小**（跨设备身份）去重；老数据没有这两项时退回按路径。
「删掉资料」的墓碑也按身份记一份（原来只记 path，另一端路径不同就删不掉、删了又回来），
合并时两种键都认。合并结果会写回本机，所以用户手上已有的重复条目下一次同步会自动收拢。

**bug 2：循环待办的"下一次"在两台设备上各长一条**

`spawnNextOccurrences`（`mod/task_runtime_mod.dart`）在用户完成一条循环待办后复制一份并
`genUid()` —— 那是**本机随机**的 uid。手机完成一次、电脑完成一次就是两个不同的 uid，
而合并按 uid 取并集 → 用户看到"两个洗头"。

修法：合并后按「来源 uid + 到期时间」折叠（同一次到期就是同一条，谁的 updatedAt 晚听谁的）。
不同到期时间的多次重照旧都留着；没有来源的普通待办不受影响。

**坚果云 503：不是偶发，是限流**

社区里 remotely-save / obsidian 那批插件踩的是同一个坑：
坚果云的 503 是**限流保护**（短时间内请求太多 / 并发太多），不是服务宕机。
（参考：<https://blog.gitcode.com/eed58f9ef5743d7b5cf639f63c552114.html>、
<https://forum-zh.obsidian.md/t/topic/44693>）

我们这边触发它的正是 **bug 1 的下载风暴**（同一批文件每轮重下）加上调试期反复重启 App。
除此之外还做了两件事：

1. `_explain(503)` 改成一句人话：「网盘暂时拒绝了这次请求（多半是限流…）过几分钟再试就好」
   —— 用户才知道该等，而不是跑去改账号密码；
2. `WebDavSyncService` 加了**退避**：一旦这轮失败原因里带 503/限流，
   30 分钟内**自动**轮询不再发请求（手动"立即同步"/下拉刷新不受影响，那是用户明确要看结果）。

我们自身的请求量并不大：没变化时一轮只有 PROPFIND `meta.json`（+ 变化时读一次 meta），
按 3 分钟一次算约 40 次/小时；附件只在真的缺文件时才 PROPFIND `files/`。
